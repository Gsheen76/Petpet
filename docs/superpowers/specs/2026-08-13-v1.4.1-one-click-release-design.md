# Petpet v1.4.1 一键发布设计

## 目标

将当前 `codex/home-scene-system` 分支中除两张本地调试截图之外的功能作为 `v1.4.1` 发布，并新增一条可复用的 Windows PowerShell 发布命令。发布提交必须安全同步到 `origin/main`；Git 标签、GitHub Release 和 `main` 必须指向同一个提交。

未来版本的入口为：

```powershell
.\scripts\release.ps1 -Version 1.4.2
```

脚本负责验证、构建、打包、Git 同步、草稿 Release、macOS 工作流、资产核验和公开发布。发布说明仍由维护者在运行脚本前编写，避免自动生成不准确的更新内容。

## 本次发布范围

- 包含当前工作树中的聊天模型与免费代理、游戏知识库、聊天 UI、头像、设置与教程、小屋及相关测试和文档。
- 更新 `version.py`、README 和 `docs/RELEASE_NOTES_v1.4.1.md`。
- 纳入 `cloudflare-worker/`、`assets/knowledge/`、`game_knowledge.py` 及相关测试。
- 将 `debug-chat-window.png` 和 `debug-pet-menu.png` 加入 `.gitignore`，不提交、不打包。
- 同步 Obsidian 的 v1.4.1 发布设计、实施计划、实施记录、发布说明和 `Petpet 总档案`。

## 采用方案

采用“本地 Windows + GitHub Actions macOS”的混合式 PowerShell 编排：

1. 本机执行 Python 测试、静态验证、Windows 构建和 EXE 冒烟。
2. 本机生成 Windows ZIP、校验和与草稿 GitHub Release。
3. GitHub Actions 使用现有 macOS Intel 与 Apple Silicon Runner，从同一个版本标签构建并上传两个 ZIP。
4. 脚本确认四个平台资产完整后才公开 Release。

该方案复用 v1.4.0 已验证的构建路径，不在本次发布中新增 Windows Actions Runner，控制变更范围。

## 脚本结构

新增 `scripts/release.ps1`，只接受明确的语义版本号，脚本内部形成以下独立阶段：

1. **Preflight**
   - 工作目录必须是 Petpet 仓库。
   - 当前分支必须是具名分支，且发布提交已经准备完成。
   - `version.py` 必须等于传入版本。
   - 对应发布说明文件必须存在。
   - 工作树必须干净。
   - `python`、`git`、`gh` 可用，`gh auth status` 成功。
   - `origin/main` 不得包含本地未知的新提交；禁止强推。
2. **Verify**
   - 运行 `pytest -q`。
   - 编译关键 Python 源码。
   - 运行 `git diff --check`。
3. **Build Windows**
   - 调用现有 `scripts/build_windows.ps1`。
   - 确认 `dist/Petpet.exe` 存在且非空。
   - 隐藏启动 EXE，保持运行数秒后仅停止精确匹配的测试进程。
   - 生成 `Petpet-v<version>-windows.zip` 和 SHA-256 清单。
4. **Publish Git source**
   - 将当前发布提交以非强制方式推送到 `origin/main`。
   - 创建指向该提交的注释标签 `v<version>` 并推送。
   - 推送后重新核对本地提交、远端 `main` 与标签对象。
5. **Draft Release**
   - 使用发布说明建立草稿 Release。
   - 上传 Windows EXE、Windows ZIP 和校验文件。
6. **Build macOS**
   - 触发 `Build macOS app`，传入现有草稿标签。
   - 等待工作流完成；任一矩阵任务失败即终止。
7. **Final gate**
   - 核对 Windows EXE、Windows ZIP、macOS Intel ZIP、macOS arm64 ZIP 均存在、非空且状态为 uploaded。
   - 记录最终资产大小和 SHA-256；macOS 文件可从 Release 下载后计算。
   - 全部满足后将草稿改为公开、非 prerelease Release。
   - 通过 GitHub API/CLI 再次核对公开状态、标签和下载 URL。

## 幂等与恢复

脚本不盲目覆盖远端对象：

- 若标签存在，只接受它已经指向当前发布提交；否则停止。
- 若 Release 存在，只接受同标签的草稿或已经完整公开的 Release。
- 若资产存在，核对名称和非空状态；不默认使用 `--clobber`。
- 若 macOS 工作流已成功并已上传资产，则跳过重复触发。
- 若发布在公开前失败，保留草稿、标签和已上传资产，输出可重新运行的同一条命令。
- 若 Release 已完整公开，重复运行只做验证并返回成功，不重复发布。

任何阶段失败都不会执行 `git reset`、`git checkout`、强推、标签覆盖或 worktree 删除。

## 测试策略

发布脚本的可判定规则先在 Python 测试中表达，再实现脚本：

- 版本号格式和 `version.py` 一致性。
- 发布说明文件存在。
- 调试截图被忽略。
- 脚本包含测试、构建、非强推 main 同步、草稿 Release、macOS dispatch、资产闸门和公开步骤。
- 工作流仍从传入标签检出并上传到草稿 Release。
- README、版本文件和发布说明一致为 `1.4.1`。

先观察新增测试因版本或脚本缺失而失败，再实现最小改动使 focused tests 通过，最后执行全量 `pytest -q`、Python 编译、`git diff --check`、Windows 构建与冒烟验证。

## v1.4.1 发布顺序

1. 完成版本、README、发布说明、脚本和 Obsidian 文档。
2. 执行全量验证并审查最终差异。
3. 创建包含当前功能的发布提交。
4. 运行一键脚本；脚本将提交同步到 `origin/main`、创建标签与草稿并编排资产上传。
5. 四项资产通过闸门后公开 v1.4.1。
6. 将最终提交、Actions run、资产大小、SHA-256、Release URL 和验证结果补入 Obsidian 实施记录及总档案。

## 明确不做

- 不自动撰写发布说明。
- 不引入完整的 Windows GitHub Actions 构建链。
- 不提交调试截图或用户配置、密钥和本地数据。
- 不签名或公证 macOS 应用；发布说明继续提示首次打开方式。
- 不删除当前 worktree 或功能分支。
